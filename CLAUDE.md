# CLAUDE.md — WellSpent-iOS

Native iOS (SwiftUI) client for WellSpent. Consumes the same ConnectRPC API as `WellSpent-web`, via the same `wellspent.v1` proto contracts published by `WellSpent-proto`.

`WellSpent.xcodeproj` lives directly at the repo root, alongside `WellSpent/` (app sources), `WellSpentTests/`, `WellSpentUITests/`, `Packages/WellSpentAPI/`, and `buf.gen.yaml` — same flat layout as the other three sub-repos. (Xcode's project-creation dialog defaults to nesting everything one level deeper, inside a `<ProductName>/` subfolder; that extra nesting was flattened out during initial setup.)

## Commands

Run all of these from the repo root (`WellSpent-iOS/`):

```bash
buf generate       # pulls proto from BSR, generates Swift into Packages/WellSpentAPI/Sources/WellSpentAPI/Gen/ (no Makefile in this repo, unlike the backend — just the raw buf command)
swift build --package-path Packages/WellSpentAPI   # fast standalone compile check of just the generated + client layer
swift test --package-path Packages/WellSpentAPI    # WellSpentAPI's own unit tests (AuthInterceptor etc.)

xcodebuild -list -project WellSpent.xcodeproj                                          # confirm scheme name
xcrun simctl list devices available                                                    # pick an installed simulator
xcodebuild -scheme WellSpent -destination 'platform=iOS Simulator,name=<device>' build
xcodebuild test -scheme WellSpent -destination 'platform=iOS Simulator,name=<device>' -only-testing:WellSpentTests
xcodebuild test -scheme WellSpent -destination 'platform=iOS Simulator,name=<device>' -only-testing:WellSpentUITests   # needs a live WellSpent-backend + UITEST_EMAIL/UITEST_PASSWORD env vars for the login/logout flows
```

If `xcodebuild`/`xcrun` says "requires Xcode" (Command Line Tools active instead of full Xcode), prefix commands with `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer`.

## Setup (new contributor)

1. Install `buf`: `brew install bufbuild/buf/buf`
2. `cd WellSpent-iOS && buf generate` — confirms Swift codegen works before anything else. `buf.build/bewellspent/wellspent` and the remote codegen plugins are public — confirmed via a fully unauthenticated run (clean `HOME`, no `buf registry login`) that no BSR token/secret is needed for this to succeed.
3. Open `WellSpent.xcodeproj` in Xcode
4. `cd ../../WellSpent-backend && make secrets-decrypt ENV=dev && make run` — API on `http://localhost:8080`; no CORS setup needed, CORS doesn't apply to native `URLSession`
5. Run the app in Simulator (⌘R) — Debug builds point at `http://localhost:8080` by default (`INFOPLIST_KEY_APIBaseURL` in the Debug build configuration)

## Architecture

- **UI**: SwiftUI only (no UIKit). Min deployment target iOS 17.0. **iOS/iPadOS only** — `SUPPORTED_PLATFORMS` is explicitly `"iphoneos iphonesimulator"` and `TARGETED_DEVICE_FAMILY` is `"1,2"` on every build configuration. Xcode's "App" template defaults new projects to multiplatform (adds `macosx`/`xros` + a "My Mac"/Vision Pro destination) unless you restrict destinations at creation time — this bit us once already (`.keyboardType(_:)`/`UIKeyboardType` are UIKit-only and don't exist on macOS, so a macOS destination fails to compile with a confusing type-checker error). If Xcode ever re-offers a "My Mac" or Vision Pro destination in the scheme picker, the project settings have regressed — re-check `SUPPORTED_PLATFORMS`/`TARGETED_DEVICE_FAMILY` in `project.pbxproj` before debugging anything else.
- **State/architecture**: MVVM using the `@Observable` macro (Observation framework) — no third-party state management. Every screen has a paired `View` + `@Observable @MainActor ViewModel`, dependencies (the ConnectRPC client) injected via `init`, not read from environment inside the view model.
- **Networking**: [connect-swift](https://github.com/connectrpc/connect-swift) — the Swift member of the same ConnectRPC family as `connect-es` (web) and `connect-go` (backend). Generated via `buf generate` against `buf.build/bewellspent/wellspent`, same BSR module the other two repos consume.
- **Concurrency**: Swift Concurrency (async/await) throughout. Note: `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` is set project-wide (Xcode's new default for SwiftUI apps) — plain logic types with no UI affinity (`JWT`, `KeychainTokenStore`, `FeatureFlags`, `APIEnvironment`) are explicitly marked `nonisolated` so they stay callable from background contexts (e.g. the networking layer's `TokenProvider` closure, which connect-swift may invoke off the main thread).
- **Local storage**: **Keychain** for the JWT only (`Auth/KeychainTokenStore.swift`, raw `Security` framework, no third-party wrapper). No local database — the app is a thin client, same as the web app; everything else is fetched live. `UserDefaults`/`@AppStorage` for simple prefs once Phase 2 needs them (locale/currency/view-mode) — not present yet, since nothing in the Auth-only phase consumes them (would be dead code).
- **Testing**: **Swift Testing** (`@Test`/`#expect`) for unit tests, **XCUITest** for a handful of end-to-end smoke flows only.

## Proto codegen (`Packages/WellSpentAPI`)

Generated Swift code is **not committed** (gitignored, same policy as `src/gen/` in web and `gen/` in backend) — always run `buf generate` after cloning or after any proto change. **This bit Xcode Cloud** (see the "Xcode Cloud" section below): a fresh clone has no `Gen/` folder and nothing runs codegen by default, so every `Wellspent_V1_*` type fails to resolve unless a `ci_post_clone.sh` script runs `buf generate` first.

`Packages/WellSpentAPI` is a **local Swift package**, not files dropped directly into the app target. Reason: Xcode's `.xcodeproj` tracks file references explicitly for anything outside a synchronized folder group; regenerating proto code that adds/removes files would otherwise mean manually re-adding references in Xcode every time. A local SPM package auto-globs its `Sources/` folder instead — regeneration is just "the file tree changed," no project-file surgery. The app target depends on `WellSpentAPI` (plus its transitive `Connect`/`SwiftProtobuf` products, added as **direct** package dependencies too — see note below) and never touches `Gen/` directly.

- `buf.gen.yaml` (repo root) — Swift plugins `buf.build/apple/swift` + `buf.build/connectrpc/swift`, output to `Packages/WellSpentAPI/Sources/WellSpentAPI/Gen/`
- `Packages/WellSpentAPI/Sources/WellSpentAPI/Client/` — hand-written wrapper (not generated, not gitignored):
  - `APIClient.swift` — `makePublicClient(baseURL:)` / `makeAuthenticatedClient(baseURL:tokenProvider:onUnauthenticated:)`, mirrors web's `publicTransport` / `createTransport(token)` in `src/lib/api/client.ts`
  - `AuthInterceptor.swift` — attaches `Authorization: Bearer <token>`, reports 401s back to the app
  - `TokenProvider.swift` — `TokenProvider`/`UnauthenticatedHandler` typealiases (plain `@Sendable` closures, not a protocol — lets the token source be a synchronous Keychain read with no actor-isolation ceremony)
  - `@_exported import Connect` / `@_exported import SwiftProtobuf` in `APIClient.swift` — lets app code reference `ProtocolClient`, `ConnectError`, `Code`, and the `.with { }` builder pattern via just `import WellSpentAPI`

**Why the app target also directly links `Connect` and `SwiftProtobuf`, not just `WellSpentAPI`:** `@_exported import` re-exports symbols at the *source* level, but under Xcode's newer "debug dylib" test-hosting mechanism, that alone isn't enough for the *linker* to find them — you'll see `Undefined symbols` for `Connect.ProtocolClient` etc. at `xcodebuild test` time even though a plain `xcodebuild build` succeeds. Fix: both `WellSpent` and `WellSpentTests` targets have explicit direct package product dependencies on `Connect` and `SwiftProtobuf` (same resolved versions `WellSpentAPI` already pulls in), not just on `WellSpentAPI`. If a future `swift test`/`xcodebuild build` (not `test`) starts failing with similar undefined-symbol errors after adding a new generated-type usage in a new file, this is almost certainly the same class of issue — check whether the target needs the same direct dependency.

## Auth flow (Phase 1)

- `WellSpentApp.swift` owns the single `SessionStore` (`@Observable`, `@MainActor`) for the app's lifetime, injected via `.environment(session)`.
- `SessionStore` mirrors web's `AuthContext` + `TransportProvider`: `publicClient` (unauthenticated, for Register/Login/ListCountries) and `authenticatedClient` (built fresh on login, torn down on logout).
- **No proactive token refresh.** `AuthService.RefreshToken` exists on the proto/backend and is available in the generated client, but nothing calls it — this matches the web app's actual current behavior (it has the same RPC available and also never calls it). On expiry, both platforms just force a re-login. If this ever changes, change it on both platforms together or note explicitly why they diverge.
- `RootView` switches between the login/register flow and `BudgetListView` based on `session.isAuthenticated`, and calls `session.refreshAuthenticationState()` on `scenePhase == .active` — the Swift equivalent of web's `visibilitychange` expiry check.
- Google OAuth: `GoogleAuthButton` is rendered disabled behind `FeatureFlags.googleAuthEnabled` (reads the `FEATURE_GOOGLE_AUTH` process environment variable, off by default) — matches web's posture exactly. Real `GetGoogleAuthURL`/`ExchangeGoogleCode` wiring (needs its own Google Cloud OAuth client + `ASWebAuthenticationSession`) is out of scope until a later phase.

## Settings (Phase 2C-3)

A `UserService`/`AuthService`-shaped feature, not `BudgetService` — lives outside `BudgetDetailView` entirely, reachable via a gear icon on `BudgetListView`'s toolbar (`.topBarLeading`) that pushes `WellSpent/Settings/SettingsView.swift` through a plain `NavigationLink`, same push mechanism already used for budget rows.

- **Single `Form`, no sub-tabs** — mirrors web's single-page `settings/page.tsx` (`ProfileSettings.tsx` + `AccountManagement.tsx` combined). Originally three sections (Profile, Change Password, Account Management); Appearance (v1.14), Plaid (Phase 4C), and Subscription (Phase 4A) were added later — see their own notes below and in "Budget flow"/"Plaid (Phase 4C)".
- **Appearance section (v1.14)** — a single `Picker("Theme", selection:)` reading/writing `@AppStorage("themeMode")` directly, no `SettingsViewModel` involvement (pure local preference, no network round trip unlike every other section here). See the "Theme toggle" roadmap entry for the full `ThemePreference`/`WellSpentApp` wiring.
- **`SettingsViewModel.load()`** fetches `GetMe` + `ListCountries` in parallel (the `ListCountries` fetch + `.filter(\.isEnabled)` is the exact same pattern as `RegisterViewModel.loadCountries()` — reused, not reinvented). `apply(_ user:)` (prefill) is internal, not private, specifically so it's unit-testable as a pure step without a live network call — `SettingsViewModelTests` calls it directly with a constructed `Wellspent_V1_User`.
- **US-gating mirrors web's actual shipped behavior, not the "more correct" mechanism**: `isUnitedStates` is a plain `countryCode == "US"` check, gating the state field, filing status picker, and tax payment frequency picker. The proto/backend do support a real per-country feature-flag mechanism (`Country.features: [CountryFeature{name, is_enabled}]`, seeded with `before_tax_income` for `US`), but web's `ProfileSettings.tsx` fetches `ListCountries` and discards `features` entirely, hardcoding the same string check — iOS mirrors that (a deliberate parity choice, not an oversight, since diverging would make iOS "more correct" than web but inconsistent with it).
- **State field is free-text** (`TextField("State (e.g. CA)", ...)`), not a 50-item dropdown — reuses the same lightweight pattern `RegisterView` already established for state, rather than introducing a new full US-states picker just for Settings.
- **Switching away from US clears the US-only fields before saving** — `saveProfile()` sends `stateCode: isUnitedStates ? stateCode : ""`, `filingStatus`/`taxPaymentFrequency: isUnitedStates ? ... : .unspecified` — confirmed live: switching a test account from `US` back to `AR` actually clears `state_code`/`filing_status`/`tax_payment_frequency` server-side, not just hides them in the UI.
- **`FilingStatusLabel.swift`/`TaxPaymentFrequencyLabel.swift`** (`Shared/`) — new label helpers following the existing `BudgetCycleLabel`/`PaymentTypeLabel`/`IncomeTypeLabel`/`RecurringTypeLabel` convention. Both are real proto enums (unlike the raw-int `transaction_type_id` pattern), so no manual wire-string mapping is needed — just `switch` on the generated Swift cases.
- **Change Password is new for iOS** — web has zero UI for `ChangePassword` despite the RPC being fully implemented and tested server-side (confirmed via research: zero callers anywhere in `WellSpent-web/src/`). Included here as a deliberate choice (confirmed with the user) since the backend fully supports it and product docs list "change their password" as a real capability; iOS is the first client to expose it. Error mapping (`SettingsViewModel.passwordChangeErrorMessage(for:)`) follows the same `ConnectError.code`-switch shape as `RegisterViewModel.errorMessage(for:)`; confirmed live that a wrong current password comes back as `invalid_argument` with a passthrough-able message.
- **Delete Account is a plain confirm `.alert`** — no typed confirmation phrase, no password re-entry, matching web's `AccountManagement.tsx` exactly. `DeleteMe` is a **soft delete** (`docs/features/delete-account.md`: sets `status = 'disabled'`, `active_until = NOW() + 30 days` server-side, confirmed live that a subsequent `Login` is blocked with a recovery-hint message) — the client's only job on success is `session.endSession()`; `RootView` already switches to the login screen on `session.isAuthenticated` becoming false, so no manual navigation/dismiss is needed.
- **`BudgetListViewModel.replaceCurrentUser(_:)`** (mirrors the existing `replaceProfile(_:)`) lets `SettingsView`'s successful `saveProfile()` update `currentUser` in place — `BudgetListViewModel.currencyCode`/`localeIdentifier` (piped into every budget screen) reflect a currency/language change immediately, no `GetMe` refetch needed.

## Budget flow (Phase 2A / 2B-1 / 2B-2 / 2B-3 / 2C-1 / 2C-2)

Phase 2A covers budgets/periods, people, and income sources; 2B-1 adds categories and payment methods; 2B-2 adds Variable transactions; 2B-3 adds Fixed expenses + mark-paid/unmark; 2C-1 adds expense allocations (Plan tab); 2C-2 adds the Expense Overview tab (actual vs. planned). Profile/account settings (2C-3) is a separate, non-budget-scoped feature — see "Settings" above.

- `WellSpent/Budget/` is the feature folder, one subfolder per management panel (`budgetList/`, `peoplePanel/`, `incomePanel/`, `categoriesPanel/`, `paymentMethodsPanel/`, `transactionsPanel/`), same layout convention as web's `src/components/budget/`.
- **`BudgetListView`/`BudgetListViewModel`** replaced the Phase 1 `HomePlaceholderView`/`HomeViewModel` stand-in — it now owns the top-level `GetMe` call (verify-email banner + the user's `currency`/`language`, used for money formatting everywhere downstream) alongside `ListBudgetProfiles`.
- **`BudgetDetailView` is the adaptive navigation shell**, not content itself: a bottom `TabView` on iPhone (`.compact` horizontal size class), a `NavigationSplitView` sidebar on iPad (`.regular`) — `BudgetSection` (`.plan`/`.transactions`/`.manage`) drives both. This collapses web's two independent nav layers (top tabs for Plan/Transactions/... *and* a separate sidebar/drawer for Income/Savings/Payment Methods/Categories/People) into one, since iOS has no good native equivalent of a persistent second nav rail alongside a tab bar. All three tabs are now real: Plan (allocations, 2C-1), Transactions (Variable + Fixed, 2B-2/2B-3), Manage (People/Income/Categories/Payment Methods). Default selected tab is `.plan` (changed from `.manage` in v1.15, once Overview was actually the more useful landing view — see below), and Plan itself defaults to its Overview sub-view, not the allocation-editing Plan sub-view.
- **`BudgetDetailViewModel.loadPeriod()` runs at the shell level** (`BudgetDetailView`'s own `.task`), not inside `BudgetManageView` — the Transactions tab needs `currentPeriod.id` for `budget_period_id` regardless of which tab loads first, so period loading can't be gated behind the user happening to open Manage. The Transactions tab shows a `ProgressView` until `currentPeriod` resolves.
- **Delete-budget dismiss must be passed down explicitly, not re-declared.** `BudgetManageView` sits inside its own nested `NavigationStack` (so People/Income/Categories/Payment Methods pushes don't disturb the other tabs), so a locally-declared `@Environment(\.dismiss)` there would only pop within that inner stack. `BudgetDetailView` captures `@Environment(\.dismiss)` at its own outer scope and passes a combined `dismissParent` closure (notify the parent list + actually dismiss) down instead. Apply the same pattern to any future tab/section that needs to close the whole budget detail screen from inside its own nested stack.
- **Removing a person** only prompts for a replacement when they have income sources attributed to them (`PersonReplacement.needsReplacement(person:incomeSources:)`, kept as a pure function in its own file so it's unit-testable without SwiftUI). **Known gap**: this doesn't check payment-method attribution even though Payment Methods now exist (2B-1) — `RemoveBudgetPersonRequest.replacement_payment_method_id` is never populated by the iOS client. Soft-delete (`is_active = false`, not a hard row delete) likely means this isn't a hard backend requirement the way `DeleteCategory`/`DeletePaymentMethod`'s replacement *is* (confirmed required via a live 401/`invalid_argument` check during 2B-1), but it should be verified and closed before Phase 3 touches People again.
- **Categories and payment methods always require a replacement on delete** — confirmed directly against the live backend during 2B-1 (`DeleteCategory`/`DeletePaymentMethod` both reject `replacement_id`/`replacement_payment_method_id` left at their zero value), unlike removing a person, where it's conditional. So `DeleteCategoryView`/`DeletePaymentMethodView` always show the picker; no `needsReplacement`-style check for either.
- **Payment type is immutable after creation** — `AddPaymentMethodView` has a type picker, `EditPaymentMethodView` doesn't (name/alias/color only), same Create/Edit-view split used for budgets in 2A (fields genuinely differ between add and edit, so two view models rather than one shared `Mode` enum like income/categories).
- **`transaction_type_id`/`transaction_frequency_id` are raw `int32` FKs on the wire, not proto enums** — their values (Fixed=1/Variable=2; One-off=1/Weekly=2/Bi-weekly=3/Monthly=4/Yearly=5) come from the seed order in `WellSpent-backend/internal/db/migrations/000001_init_schema.sql`, not a generated type, so every place that uses them has a doc comment pointing back at that migration. `TransactionsViewModel.variableTypeID`/`FixedExpensesViewModel.fixedTypeID` are the one source of truth for `2`/`1`; `AddEditTransactionViewModel` derives `transactionFrequencyID` from the `recurring` toggle (`recurring ? 4 : 1`).
- **Spent/Received sign convention** (`docs/features/negative-positive-transactions.md`): the Variable add/edit form always takes a positive amount plus a segmented Spent/Received toggle; `amount >= 0` = Spent (red, `-` prefix), `amount < 0` = Received (green, `+` prefix). `TransactionAmountFormatting.swift` holds this as pure, unit-tested logic — never inline a sign check in a view. **Fixed expenses have no sign flip** — always a plain expense, shown via `MoneyFormatting.format` directly, not `TransactionAmountFormatting`.
- **Not yet ported from web, deliberately deferred**: Fixed expense payment-plan fields (`end_date`/`total_payments` — web's bidirectional end-date↔total-payments computation); "not due yet" placeholder rows for active Fixed templates whose anchor date hasn't spawned a transaction yet this period (lower priority since `CreateFixedExpenseResponse` returns the spawned transaction directly, so a freshly created template shows up immediately in the common case). All real web behaviors, just not in scope yet — note before assuming Fixed-expense scheduling fully matches web. (The Income-category-always-excluded rule *is* now implemented — see 2C-2 below — `TransactionsViewModel`/`FixedExpensesViewModel`'s `totalText` both use it. Search/filters — "Spent only"/"Exceeded only"/"Excluded only" — and day-grouping are also now implemented, v1.15, see below.)
- **Fixed expenses live inside the Transactions tab, not a separate Manage panel** — mirrors web exactly (`TransactionsPanel.tsx`'s Fixed/Variable toggle over spawned `Transaction` rows, not a standalone `FixedExpense` list). `TransactionsListView` owns a `TransactionKind` (`.variable`/`.fixed`) segmented picker; `FixedExpensesListView` is the Fixed sub-view, each with their own toolbar "+" that only contributes to the shared toolbar while its content is actually on screen (SwiftUI composes `.toolbar` modifiers from whichever descendant view is currently in the hierarchy — no manual coordination needed since only one of the two is ever mounted at a time).
- **Mark-paid amount propagation to the template is entirely backend-side** — confirmed live: marking a Fixed transaction paid with an amount different from `planned_amount` automatically updates the linked `FixedExpense.planned_amount`. The iOS client only calls `MarkTransactionAsPaid`; never a follow-up `UpdateFixedExpense`.
- **`anchor_date` is the only date the user picks**; `day_of_month`/`day_of_week` are always derived from it client-side (`FixedExpenseScheduling.swift`, pure + unit-tested) since `CreateFixedExpenseRequest`/`UpdateFixedExpenseRequest` carry them as plain non-optional `int32` fields with no "compute this yourself" flag.
- **Established `Shared/` label/formatting/input helpers** (all `nonisolated enum`s with static functions, mirroring web's small formatting hooks): `Money+Formatting.swift`, `MoneyInput.swift` (shared `parseAmount`/`formatForEditing` for every money text field), `TransactionAmountFormatting.swift` (home to `sum(_:)`, the shared nanos-carry addition logic — handles both overflow and underflow for negative amounts — used by `totalDisplayText` and by `ExpensePlanCalculations`), `FixedExpenseScheduling.swift`, `ExpensePlanCalculations.swift` (2C-1, below), `BudgetCycleLabel.swift`, `BudgetRoleLabel.swift`, `IncomeTypeLabel.swift`, `RecurringTypeLabel.swift`, `PaymentTypeLabel.swift`. Reuse this pattern for any new proto enum/parsing/derivation rule rather than inlining in a view or view model. `PresetColors.all` (a fixed hex list) is the shared source for every optional-color picker (people, categories, payment methods); `HexColor.swift` (`Shared/`, since v1.13) is the real `Color(hexString:)`/`toHexString()` parser — see the "Entity color picker fix (v1.13)" entry near the bottom of this section for why a parser exists now.
- **Expense Plan tab (2C-1)** — `WellSpent/Budget/expensePlanPanel/`. A per-category planned total (`ExpensePlanCalculations.plannedTotal`, pure + unit-tested, mirrors web's `getCatPlanned`): the Savings system category always sums `SavingsSource.amount`; every other category sums `ExpenseAllocation.plannedAmount` across people, and only if that's zero falls back to the sum of the current period's Fixed-type transactions' `plannedAmount` for that category — allocations and the fixed fallback are never combined. Categories are visible only if that total is nonzero; visible ones sort by planned total descending (`docs/features/category-list-order.md`). **Exclusion (`is_excluded`) does not affect planned totals** — confirmed live (excluding a Fixed transaction still counts its `plannedAmount` toward the category total); it only matters for Overview's actuals (2C-2, not built yet).
- **Allocation edits are per (category, person), not a single form** — tapping a category row opens `AllocateCategoryView`, one amount field per `BudgetPerson`, prefilled from any existing allocation. `AllocateCategoryViewModel.computeChanges` is the pure diff: a nonblank valid amount becomes an `UpsertExpenseAllocation` call, a row that had an allocation but is now blank becomes `DeleteExpenseAllocation`, and a row that was already blank stays untouched (no allocation created for a still-zero row). Same "sheet computes the value, parent view model performs the network call" split as `MarkAsPaidView` — `ExpensePlanViewModel.applyAllocationChanges` is the one that actually calls the RPCs and reloads.
- **Adding a not-yet-visible category to the plan** uses a flat picker sheet (`AddPlanCategoryView`, categories minus already-visible ones) rather than nesting a second sheet inside a sheet — selecting one dismisses the picker and `ExpensePlanView` presents `AllocateCategoryView` for it next. This replaces web's free-text "pin a category" Autocomplete with a simpler native equivalent.
- **"not due yet" fixed-expense placeholder rows are still deferred** in the Plan/Overview planned total (same deferral as 2B-3, carried over — only current-period Fixed transactions count toward the fallback, not templates that haven't spawned one yet).
- **Expense Overview tab (2C-2)** — `ExpensePlanView` gained a `Picker("View", selection:)` (`PlanKind`: `.plan`/`.overview`, local to the file, same pattern as `TransactionKind` in `TransactionsListView.swift`) switching between the existing Plan content and new `ExpenseOverviewListView`; toolbar "+" only shows for `.plan`. `ExpenseOverviewCalculations.swift` (`Shared/`) is the pure actual-spend helper, mirroring web's `computeActualTotals`: excludes manually-excluded and Income-category transactions (`isTransactionExcluded`), skips unpaid Fixed-type transactions from actual spend, attributes each transaction to a person via `paymentMethodID` → `PaymentMethod.budgetPersonID` (0 = unattributed), and buckets categoryless transactions into a separate "Uncategorized" total rather than dropping them. `ExpenseOverviewViewModel` reuses `ExpensePlanCalculations.plannedTotal` unchanged for the category-level planned figure, and calls it a second time with person-filtered inputs (allocations/savings/fixed amounts filtered to one person) to get the per-person planned figure — no new planned-total logic needed. Category sort/visibility reuses `ExpensePlanCalculations.sortedVisibleCategories`, just keyed on actual instead of planned, per `docs/features/category-list-order.md`.
- **Income total in Overview comes from `ListIncomeEntries` (period-scoped), not `ListIncomeSources`** (which Plan uses) — Overview is about what actually happened this period. **Known lifecycle gotcha, confirmed live**: adding an `IncomeSource` after a period already exists does not retroactively create an `IncomeEntry` for that period — there's no `AddIncomeEntry` RPC; entries only spawn when a new period is generated (same pattern as Fixed expenses spawning transactions). A test budget set up income-source-after-period will show $0 income in Overview; this is expected backend behavior, not an iOS bug.
- **Overspend is `planned > 0 && actual > planned`**, at both category and person level (`ExpenseOverviewCalculations.isOver`), shown as a red `+$X` chip. First use of `DisclosureGroup` (category → per-person breakdown) and Swift Charts (`import Charts`, a single `BarMark` per visible category, red when over budget else `.accentColor`) in this codebase — no third-party charting dependency, native framework only. Category/person colors are intentionally **not** parsed into `Color` for the chart — the chart's own color logic (red-when-over vs. `.accentColor`) is unrelated to entity color, so there was never a reason to plumb it through here even after `HexColor.swift` added a real parser (v1.13).
- **Deliberately deferred from web's Overview**: the per-category expanded transaction list (`CategoryTransactionList` — the Transactions tab already covers browsing all transactions); the percent-of-total chip (found in web's code but not in `docs/features/expense-overviews.md`'s business rules).
- **Every `View` struct has a `#Preview`** — a running requirement now, not just a 2B-3 cleanup. Views that hit the network use a throwaway unreachable `ProtocolClient` (`http://localhost:1`, same as the test suite's convention) so the canvas still renders the loading/empty state; views driven directly by init params (edit forms, delete/mark-paid pickers) get realistic sample proto values so they render fully populated.
- App version is now surfaced (`BudgetListView`'s footer, reading `Bundle.main.infoDictionary["CFBundleShortVersionString"]`) — bump `MARKETING_VERSION` in the **`WellSpent` app target's** Debug/Release configs only (not the test targets) per the existing patch/minor/major convention, now that there's a UI surface for it. (2B-1/2B-2 shipped without a bump — an oversight caught and corrected in 2B-3; don't repeat it.)
- **Every budget sub-screen's `.task` must always call `load()`, not just on first appearance (fixed post-2C-2, v1.4.1)** — the original pattern across every panel (`ExpensePlanView`, `ExpenseOverviewListView`, `TransactionsListView`, `FixedExpensesListView`, `IncomeListView`, `PeopleListView`, `CategoriesListView`, `PaymentMethodsListView`) was `guard viewModel == nil else { return }` before creating + loading — meaning once a tab had been visited once, switching away and back (TabView on iPhone, or the `NavigationSplitView` detail switch on iPad) never refetched, so edits made on one tab wouldn't show up on another without leaving `BudgetDetailView` entirely and pushing back in. Fixed by changing every one of these to `if viewModel == nil { viewModel = X(...) }` followed by an unconditional `await viewModel?.load()` — creates the instance once, but reloads its data on every reappearance. Every one of these views also now has `.refreshable { await viewModel?.load() }` for manual pull-to-refresh. **When a screen has a nested picker over two sub-views that each own a List** (`TransactionsListView`'s Variable/Fixed, `ExpensePlanView`'s Plan/Overview), both the outer view *and* the inner sub-view need their own `.refreshable` — SwiftUI's `.refreshable` is environment-based and would otherwise apply the *outer* view model's reload to the *inner* view's List. `BudgetListView` (the budgets list, outside `BudgetDetailView`) was left as-is — it already had `.refreshable` and handles staleness via explicit array-mutation callbacks (`addCreatedProfile`/`dismissAfterDelete`) rather than a full reload, which is a deliberate, different pattern for that screen.

- **`TransactionAmountFormatting.sum` crashed on real production data — Plan tab crashed on launch (fixed, found via a live TestFlight crash report)** — `sum(_:)` accumulated `nanos` as `Int32` across the whole loop, carrying into `units` only once at the end. Each individual `Money` value's `nanos` is bounded to ±999,999,999, but the *running* accumulator isn't — three entries with large fractional cents (e.g. three `$X.99` amounts) already exceeds `Int32.max` (~2.147B) before the loop finishes, and Swift's `+=` traps with a fatal arithmetic-overflow error rather than silently wrapping. `ExpensePlanViewModel.incomeTotal`/`committedTotal` calls this across every income source/category, so on an account with enough real entries it crashed on the very first load of the (now-default, since this session's earlier work) Plan/Overview tab. **Diagnosed from an actual TestFlight crash stack trace supplied by the user** (Xcode Organizer's Crashes tab, not Apple's own crash-report popup — that one only reaches Apple, not the dev team; see the note below about adding real crash reporting), not guessed. Fix: accumulate `nanos` as `Int64` during the loop (effectively unlimited headroom for any realistic transaction volume), narrowing back to `Int32` only once at the end, after the carry guarantees it's back in range. `units += amount.units` was never at risk — `Int64`'s range has no realistic exposure for money amounts.

- **Entity colors missing from most of the app, not just the Plan tab (fixed, v1.18.0, [GitHub issue #25](https://github.com/BeWellSpent/WellSpent/issues/25))** — the reported bug ("categories not showing colors on expense plan") turned out to be one symptom of a much wider gap: outside the v1.13 color-picker fix's own touch points (`CategoriesListView`, `PaymentMethodsListView`, `PeopleListView`), almost nowhere else in the app showed a category/person/payment-method's color — not Plan, not Overview, not Transactions/Fixed rows, not Income/Savings rows, and not a single `Picker` anywhere (Add/Edit Transaction, Add/Edit Fixed Expense, Add Plan Category, Add/Edit Savings Source, Add/Edit Income, Add Payment Method, the three replacement/reassignment pickers, all three budget-setup-wizard pickers, Invites' "Link to person" picker). Confirmed scope directly with the user rather than assuming the issue's literal title was the full ask — expanded twice: first to cover person/payment-method (not just category) display everywhere, then explicitly to include picker/dropdown menus, not just list rows.
  - **`Shared/ColorDotView.swift`** gained `ColorDotLabel` — a `Label { Text(title) } icon: { ColorDotView(hex: hex, diameter: 10) }` wrapper, purpose-built for `Picker` `ForEach` options (a plain `HStack` reads oddly as a picker row; `Label` is the idiomatic shape there). Existing `ColorDotView` usage pattern (`HStack { ColorDotView(hex:); Text(name) }`) was reused as-is for every list-row site — no new component needed there.
  - **~20 files touched**, one consistent pattern throughout — list rows get an `HStack`-prefixed dot, pickers get `ColorDotLabel`: `ExpensePlanView`/`ExpenseOverviewListView` (category + person rows), `TransactionsListView`/`FixedExpensesListView` (category + payment-method dots, via new `categoryColor(for:)`/`paymentMethodColor(for:)` helpers added next to each view model's existing `*Name(for:)` lookups), `IncomeListView`/`SavingsListView` (person + payment-method dots, same helper pattern), `AddEditTransactionView`, `AddFixedExpenseView`/`EditFixedExpenseView`, `AddPlanCategoryView`, `AddSavingsSourceView`/`EditSavingsSourceView`, `AddEditIncomeView`, `AddPaymentMethodView`, `DeleteCategoryView`/`DeletePaymentMethodView`/`RemovePersonView` (replacement pickers), `IncomeSetupStepView`/`PaymentMethodsSetupStepView`/`PeopleSetupStepView` (budget-setup wizard), `InvitesListView` ("Link to person" picker — found in a final grep sweep after the initial file list, since it wasn't caught by the `Picker("Person"`-style searches used to build that list).

  - **Not independently verified against a running backend with real multi-color data in this pass** — build succeeded, the full `WellSpentTests` suite passed (0 failures), and `WellSpentUITests` (including `BudgetSmokeTests`) compiled cleanly via `build-for-testing`, but no local `WellSpent-backend` instance was available in this environment to log in and visually confirm dot placement against real colored categories/people/payment methods end-to-end. Do a real Simulator-against-local-backend pass before treating the visual result as fully confirmed.
- **Color dots still didn't show in the *collapsed* picker value — a native `Picker` can't do that (fixed, v1.19.0, [GitHub issue #28](https://github.com/BeWellSpent/WellSpent/issues/28))** — user-reported follow-up to #25/v1.18.0: list rows were fine, but every category/person/payment-method `Picker` (the ~13 sites converted to `ColorDotLabel` in v1.18.0) still showed no dot in its own collapsed trailing value, only text — because SwiftUI's `Picker` renders a `Label`'s icon inside its *expanded* options only; the collapsed value is text-only, a hard platform limitation, not a bug in the v1.18.0 fix. Web's `AddTransactionModal` avoids this via MUI `Select`'s `renderValue` prop, which fully customizes the closed-state display.

- **Editing a Fixed expense could silently reschedule its entire recurring cadence, not just show a stale date (fixed, v1.19.0, same issue #28)** — user-reported: editing any Fixed expense (even an unrelated field like the name) sometimes changed its schedule. Root cause: `fixed_expense.anchor_date` is a nullable column added later (migration `000025`, "NULL preserves today's behavior exactly") — an *optional* override on top of the real schedule (`day_of_month`/`day_of_week`). Any expense created before it existed, or without one explicitly set, legitimately has `anchor_date = NULL`, and the backend's due-month math (`fixedExpenseAnchor`, `budget_profile_service.go`) falls back to `created_at` in that case — which is what actually drives which months an interval>1 (e.g. quarterly) expense is due in. `EditFixedExpenseViewModel.swift` used to send `anchorDate` **unconditionally** on every save (falling back to `Date()` — today — when there was no existing anchor), so saving *any* edit on a legacy expense silently gave it a brand-new `anchor_date`, potentially shifting its entire due-month cadence.
  - **Fix has two parts**: (1) `FixedExpenseScheduling.displayDate(dayOfMonth:dayOfWeek:isWeekly:referenceDate:)` (new, pure, unit-tested) reconstructs a display-only date that actually reflects the stored `day_of_month`/`day_of_week` — clamped to the reference month's real length, or remapped to the correct ISO weekday — instead of defaulting to today; (2) `EditFixedExpenseViewModel` now tracks `hadAnchorDate`/`initialStartDate` at init and only includes `anchor_date` in the `UpdateFixedExpenseRequest` if the expense already had one, or `startDate` actually changed from its initial (real-or-reconstructed) value — exposed as `shouldSendAnchorDate`, a small testable property, specifically so the core fix is unit-testable without mocking the network call.
  - **Scoped to iOS only** — confirmed with the user that web doesn't reproduce this; `EditFixedExpenseModal.tsx`'s superficially similar fallback wasn't touched.
  - **Tests**: `WellSpentTests/EditFixedExpenseViewModelTests.swift` — `alwaysSendsAnchorDateWhenAlreadyPresent`, `onlySendsAnchorDateForLegacyExpenseWhenDateChanged`, `legacyPrefillPreservesDayOfMonth`; `WellSpentTests/FixedExpenseSchedulingTests.swift` — `displayDatePreservesDayOfMonth`, `displayDateClampsToShorterMonth`, `displayDateRoundTripsWeekly`.
  - See `WellSpent-backend/CLAUDE.md` for the third bug fixed under the same issue (payment method going blank after period cycling) — backend-only, no iOS changes needed there beyond the data itself being correct once backfilled.

## Testing

- **Swift Testing**, one `@Suite` per type, in `WellSpentTests/` (app target logic) and `Packages/WellSpentAPI/Tests/WellSpentAPITests/` (networking layer). Covers: JWT decode/expiry edge cases, Keychain round-trips (real Simulator Keychain — works fine under `xcodebuild test`, each test uses a unique service name to avoid cross-test interference), `AuthInterceptor` header injection and 401 handling (constructed `HTTPRequest`/`ResponseMessage` values directly, no network mocking needed), view model validation + error-code-to-message mapping, `SessionStore` state transitions.
- Deliberately **not** unit tested: SwiftUI view bodies (no assertion value without a UI-test harness) and thin one-line pass-throughs to generated RPC methods.
- **XCUITest** smoke flows in `WellSpentUITests/`: `LoginSmokeTests` (valid + wrong-password), `RegisterSmokeTests` (fresh timestamp-suffixed email — no seeded account needed), `LogoutSmokeTests` (log out, then relaunch *without* the reset flag to prove the Keychain token was actually cleared, not just in-memory state), `BudgetSmokeTests` (create a budget, add a person, add an income source, then delete the budget as cleanup so repeated runs don't leave orphan data on the real backend). Login/Logout/Budget tests need a seeded account: `export UITEST_EMAIL=... UITEST_PASSWORD=...` before running. All need `WellSpent-backend` running locally.
- The app supports a `-uiTestResetSession` launch argument (checked in `WellSpentApp.init`) that clears the Keychain token before `SessionStore` restores a session — every UI test starts from a known logged-out state instead of inheriting whatever the Simulator's Keychain has from a previous run.
- Accessibility identifiers are set explicitly on every interactive element and screen-level container (not inferred from label text) — i18n will change label text later, identifiers won't.
- **Never use screenshots to verify UI behavior** (`xcrun simctl io screenshot`, AppleScript/System Events clicks, or any other visual-inspection loop) — reading an image back into context is expensive, and a single verification pass can burn a large amount of context for one data point. If you need to confirm rendering behavior empirically (e.g. "does this SwiftUI view actually render X"), write it as an XCUITest assertion instead (`XCTAssertTrue(element.exists)`, `.isHittable`, accessibility-tree queries) — these are cheap, repeatable, and don't require reading pixels back into context. If no automatable signal exists for what you're checking, say so explicitly and ask the user to look rather than screenshotting yourself.

## Git workflow

Same convention as the other sub-repos: work happens on `develop`, never directly on `main`.

```bash
git checkout develop   # or: git checkout -b develop, if it doesn't exist yet locally
git add WellSpent/... Packages/WellSpentAPI/Package.swift Packages/WellSpentAPI/Sources/WellSpentAPI/Client/... Packages/WellSpentAPI/Tests/...

```

**Do not push automatically.** Wait for the user to manually validate the change and give explicit go-ahead before running `git push`. Once pushed, open a PR from `develop` to `main`:

```bash
git push origin develop
gh pr create --base main --head develop --title "Short title" --body "Description"
```

No auto-merge — this repo has no CI yet, so the PR is left for the user to merge manually (unlike the other three sub-repos, which enable `gh pr merge --auto`). Revisit once CI exists here.

## Xcode Cloud

`ci_scripts/ci_post_clone.sh` runs `buf generate` right after Xcode Cloud clones the repo, before dependency resolution/build — without it, every archive/build fails with dozens of `cannot find type 'Wellspent_V1_*' in scope` errors, since the gitignored `Gen/` folder above doesn't exist in a fresh CI clone and nothing else populates it. Discovered via a real failed archive build (`xcodebuild-archive.log`) — the errors span nearly every file that imports `WellSpentAPI`, which is the signature of this exact class of problem (missing generated code), not a real compile bug in any of those files.

- Installs `buf` via Homebrew (pre-installed on Xcode Cloud's macOS images specifically to support this kind of setup step) with `HOMEBREW_NO_AUTO_UPDATE=1` to skip an unnecessary, slow `brew update` in an ephemeral CI environment.
- Runs `buf generate` from `$CI_PRIMARY_REPOSITORY_PATH` (Xcode Cloud's env var for the cloned repo root, where `buf.gen.yaml` lives).
- **No BSR authentication needed** — confirmed directly by running `buf generate` with a completely clean `HOME` (no cached `buf registry login` state): `buf.build/bewellspent/wellspent` and the remote codegen plugins (`buf.build/apple/swift`, `buf.build/connectrpc/swift`) are public. If a future proto module ever becomes private, this script would need a `BUF_TOKEN`-equivalent secret configured in Xcode Cloud's environment and a `buf registry login` step added here.
- Per Apple's Xcode Cloud docs, `ci_scripts/` must sit at the same level as the `.xcodeproj` (or repo root) — both coincide here since `WellSpent.xcodeproj` already lives at this repo's root.
- **Not yet verified with a real Xcode Cloud run** (added reactively after reading one failed build's log, not proactively tested) — confirm the next Xcode Cloud archive actually succeeds before treating this as done.
